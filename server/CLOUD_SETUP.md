# Подключение Yandex Cloud

Цепочка: ESP32 → WAV → SpeechKit → текст → YandexGPT → проверенный JSON → таблица.
Код интеграции готов. Реальные вызовы пока не проверены: API-ключ ещё не настроен.
Все автоматические проверки используют подменённое облако и не расходуют баланс.

## Что нужно сделать в аккаунте

1. Войти в [консоль Yandex Cloud](https://console.yandex.cloud/).
2. Создать облако и каталог в регионе Россия, подключить платёжный аккаунт.
   Этот вариант использует SpeechKit API v1; для региона Казахстан потребуется другой API.
3. Создать сервисный аккаунт в этом каталоге.
4. Назначить ему роли на каталог:
   - ai.speechkit-stt.user;
   - ai.languageModels.user.
5. Создать API-ключ сервисного аккаунта с областями:
   - yc.ai.speechkitStt.execute;
   - yc.ai.languageModels.execute.
6. Скопировать идентификатор каталога.
7. Заполнить server/secrets.json локально. Не присылать ключ в чат и не добавлять его в Git.
   Файл уже создан с пустыми значениями; secrets.example.json — шаблон для репозитория.

    {
      "YANDEX_API_KEY": "ключ сервисного аккаунта",
      "YANDEX_FOLDER_ID": "идентификатор каталога",
      "YANDEX_GPT_MODEL": "yandexgpt/latest"
    }

Можно вместо файла задать одноимённые переменные окружения; они имеют приоритет.
После изменения ключа нужно перезапустить сервер.

Облачные запросы оплачиваются по тарифам провайдера. Создание платёжного аккаунта,
пополнение и реальные платные запросы автоматически не выполнялись.
Настрой лимит бюджета в кабинете. Ключ хранится только на компьютере, ESP32 его не получает.

Официальная документация:
[аутентификация SpeechKit](https://aistudio.yandex.ru/en/docs/speechkit/concepts/auth),
[области API-ключей](https://yandex.cloud/ru/docs/iam/concepts/authorization/api-key),
[синхронное распознавание](https://aistudio.yandex.ru/ru/docs/speechkit/stt/api/request-api),
[структурированный вывод](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/structured-output),
[TextGeneration API](https://aistudio.yandex.ru/ru/docs/ai-studio/text-generation/api-ref/TextGeneration/completion).

## Запуск

Из корня репозитория:

    py -m pip install -r server/requirements.txt
    & ./server/start_server.ps1

Проверка: http://127.0.0.1:8000/health — cloud_configured должно быть true.
Это проверка наличия настроек, а не действительности ключа или баланса.
Действительность проверяется первым реальным запросом.

Загрузить обновлённую firmware/voice_planner/voice_planner.ino с OPI PSRAM.
Сеть, адрес сервера и GPIO остаются прежними. Монитор порта — 115200.

Для первого теста произнести:
«Завтра в шесть вечера сделать лабораторную по физике. Ещё купить хлеб».

После отпускания кнопки WAV сохраняется сразу, ESP32 получает job_id и показывает
PROCESSING. Облако обрабатывается последовательно, в фоне. ESP32 проверяет статус
отдельной сетевой задачей, поэтому ожидание распознавания не блокирует запись.

После обработки должна появиться таблица из двух задач. Проверить текст и дату в
http://127.0.0.1:8000/planner.json и в JSON рядом с записью.
«Завтра» вычисляется относительно времени приёма записи сервером, UTC+03:00,
а не времени окончания обработки. При повторной обработке дата отсчёта сохраняется.

## Файлы и формат

- server/recordings/имя.wav — исходная запись.
- server/recordings/имя.json — текст и задачи именно этой записи.
- server/data/planner.json — общий список, отсортированный по срокам.
- server/tasks.db — SQLite: задания обработки и задачи.

Пример оформления и формата: examples/planner.example.json.
Это вручную подготовленные демонстрационные данные, не результат реального запроса.
Схема облачного ответа задаётся CommandBatch / PlannerCommand в task_models.py;
TaskDraft описывает поля нового дела.
Текст, дата и время сохраняются в UTF-8; отсутствующие дата/время — null.
needs_clarification отмечает неоднозначности; note содержит пояснение.
priority принимает low, normal, high. Новые дела имеют status=pending.
schema_version=2: tasks содержит активные дела, archived_tasks — выполненные и
удалённые. У каждого дела есть постоянный number; он не меняется при сортировке,
восстановлении и перезапуске. clarifications содержит запросы на уточнение.
Файл рядом с WAV хранит исторический результат именно этой записи, включая actions:
applied, unchanged или needs_clarification. Текущее состояние — в общем planner.json.

Ответ модели проверяется сервером: неизвестные поля, неверная дата, неподдерживаемое
время и другие нарушения схемы приводят к ошибке всей записи без частичного добавления.
Совпадение схеме не гарантирует правильное понимание фразы: первые результаты нужно
проверить по распознанному тексту и JSON. Непонятные сроки не следует считать подтверждёнными.

Поддерживаются добавление, удаление, выполнение и восстановление дел.
Редактирование названия/срока, массовые операции с фильтрами и автоматические повторы пока
не поддерживаются: такие команды требуют уточнения, а не скрытого изменения данных.

## Экран

Сервер рисует готовый 1-битный кадр 184 × 384 (8832 байта), ESP32 применяет поворот
и коррекцию панели. Шрифт с кириллицей используется на сервере:
Arial в Windows или DejaVu Sans в Linux. Можно задать PLANNER_FONT — путь к TTF.
Сам файл шрифта в репозиторий не копируется.

На странице шесть строк: дата с годом, время, название. Длинное название сокращается
на экране, но полностью сохраняется в JSON. ? означает уточнение, ! — высокий приоритет.
Команда n в Serial Monitor переключает страницу. Номер страницы и общее число дел
показаны внизу. В отсутствие нового задания таблица проверяется раз в 15 секунд.
После пяти частичных кадров экран ждёт следующего завершения записи для полной
очистки: при длительном перелистывании без записи новые кадры могут быть отложены.

## Если что-то не получилось

- CLOUD NOT SET — ключ и каталог не заполнены; WAV сохранён, облако не вызывалось.
- CLOUD FAILED — открыть http://127.0.0.1:8000/jobs, посмотреть error у записи.
- PROCESSING — идёт обработка, результат ещё не получен.
- TABLE OFFLINE — задача обработана, но не удалось скачать кадр таблицы.
- STATUS OFFLINE — нет связи с локальным сервером.

Интерактивное описание API: http://127.0.0.1:8000/docs.
После настройки ключа старую запись можно обработать через POST /jobs/{job_id}/retry.
Без заполненного ключа этот маршрут возвращает 409. Завершённая запись повторно
не обрабатывается. Неудачный разбор повторяется явно, автоматических платных повторов нет.
Если текст уже был распознан, повтор использует его и снова вызывает только YandexGPT.
При потере ответа SpeechKit повтор может потребовать ещё одного оплачиваемого распознавания.

X-Recording-Id в запросе ESP32 защищает повторную отправку того же WAV от дубликатов.
Новая запись получает новый идентификатор. Для очередной независимой записи с тем же
текстом будет создано новое дело — смысловое объединение дубликатов пока не выполняется.

## Проверки без облака

    & ./server/run_checks.ps1

Проверяются WAV/HTTP, повторная загрузка, отсутствие конфигурации, облачный разбор с
подменённым транспортом, строгий формат задач, сохранение JSON, повторы и таблица.
Настоящие адреса облачных сервисов тестами не вызываются.

## Работа при сбоях и остановке

Временная ошибка SQLite или файлового хранилища не останавливает обработчик очереди.
Если обработка уже началась и прервалась, задание помечается ошибкой, а оплачиваемая
операция автоматически не повторяется. Остальные задания продолжают обрабатываться.
Наличие работающего обработчика видно в /health, поле worker_running.

При Ctrl+C сервер ждёт завершения уже запущенного запроса и сохранения его результата.
Поэтому остановка во время облачного запроса может занять время.
Экспорт JSON использует отдельные временные файлы и атомарную замену; параллельные
чтения общего списка не перезаписывают файл.

## Голосовое управление делами

После обновления перезапустить только сервер. Прошивка и ключ остаются прежними.
Существующая SQLite-база обновляется автоматически: прежние дела сохраняются и
получают номера. Номера не переиспользуются после удаления.

| Произнесённая команда | Действие |
| --- | --- |
| «Удали все события» / «Удали все дела» / «Удали всё» | Убрать все активные дела в архив |
| «Удали задачу купить хлеб» | Найти активное дело по названию и убрать из списка |
| «Удали задачу номер пять» | Удалить одно дело с постоянным номером 5 |
| «Отмени последнее добавленное дело» | Удалить одно последнее активное дело по порядку добавления |
| «Лабораторная по физике выполнена» | Отметить дело выполненным |
| «Верни задачу номер пять» | Вернуть удалённое или выполненное дело в активный список |
| «Отмени последнее удаление» | Восстановить последнее удалённое дело, которое ещё находится в архиве |

Номер показывается перед названием в колонке «№ / Дело». Название сопоставляется
с каталогом моделью, затем сервер проверяет единственность совпадения.
Если одинаковых активных дел несколько, ничего не меняется; внизу экрана появляется
«? Повторите команду с №». Нужно произнести полную команду, например:
«Удали задачу номер два». Одна фраза «номер два» сама по себе не является подтверждением.
Подробности и номера кандидатов доступны в /jobs/{id} и clarifications в /planner.json.

Для номера поддерживаются цифры и русские числительные после слова «номер»
(например, «номер двадцать пять»). Если номер не был произнесён, модель не может
выбрать его вместо пользователя. Можно уточнить название явно названной датой/временем.
Удаление по названию предпочитает активное дело его ранее выполненному одноимённому
варианту; для выбора архивной записи лучше использовать номер.

Удаление мягкое: записи остаются в SQLite со статусом deleted, выполненные — done.
Оба состояния скрыты из активной таблицы, но видны в archived_tasks общего JSON.
История команд хранится в task_events. Исходные WAV и JSON записей сохраняются.
Восстановление возвращает исходные номер, название и срок.

Одна диктовка может содержать несколько команд; они применяются по порядку.
Неоднозначная команда не меняет дела, но однозначные команды той же диктовки
могут выполниться. При нарушении JSON-схемы не применяется вся запись.
Повтор завершённого задания не исполняет команды заново.
При повторе старого неудачного задания не выбираются добавленные позднее дела
и не отменяются более новые изменения статуса: вместо этого запрашивается уточнение.

## Удаление всех дел

Команда del добавлена в промпт, JSON-схему и серверный обработчик.
Произнеси «Удали все события», «Удали все дела» или «Удали всё».
Удаляются все активные дела (status=pending); выполненные и прежний архив не меняются.
Физического удаления из SQLite, WAV и файлов истории не происходит.
В результате команды в actions сохраняются count и список затронутых tasks.

Удаление по фильтру («все на завтра», «всё кроме ...») пока не поддерживается:
сервер просит уточнить команду. Одной просьбы удалить конкретное дело недостаточно
для массовой операции, даже если модель ошибочно вернёт del.

Запрос выполняется в одной транзакции с историей всех затронутых дел.
Старая структура task_events автоматически обновится при перезапуске сервера,
существующая история сохраняется. Прошивку ESP32 менять не нужно.
Повтор завершённого запроса не затрагивает новые дела. Если при повторе старого
неудачного запроса обнаружены более новые изменения статусов, массовая операция
не применяется частично — потребуется новая запись.

Отдельное дело возвращается командой «Верни задачу номер пять».
«Отмени последнее удаление» по-прежнему возвращает одно дело, а не всю массовую очистку.
